# Changelog

All notable changes to Kestrix are documented here.

## [Unreleased]

### Added

- Release publishing: pushing a `vX.Y.Z` tag now builds the production image, publishes it to the GitLab Container Registry as `registry.gitlab.com/kestrix/kestrix:<tag>` and `:latest`, and creates a GitLab Release with the matching changelog section and the stripped Linux amd64 binary attached. `kestrix version` (and the existing `GET /api/version` / UI footer) now report the released tag instead of `dev` on any build produced by `make build-release` or the release pipeline. `docker/docker-compose.prod.yml` defaults to the registry `latest` image; pin `KESTRIX_IMAGE` to a specific tag for a reproducible deployment. `scripts/release.sh <X.Y.Z>` is the maintainer entry point for cutting a release; see [Usage](docs/usage.md#cutting-a-release).
- Run concurrency limit, queueing, retention, and an output bound: `KESTRIX_RUNNER_MAX_CONCURRENT_RUNS` (default `2`, also `runner.max_concurrent_runs` in the config file) bounds how many runs execute at once. A run triggered while every slot is busy is recorded `queued` - visible in `GET /api/runs`, `GET /api/projects/{name}/runs`, the dashboard counters, and the UI with its own status chip and counter tile - and starts automatically, in acceptance order, as slots free; cancelling a `queued` run marks it `canceled` without executing anything and frees its place for the next queued run. Whole-pipeline runs, single-task re-runs, and approved manual tasks each occupy one slot while executing. `KESTRIX_RUN_HISTORY_LIMIT` (default `1000`, also `runner.run_history_limit`) bounds retained runs: once a run finishes, the oldest terminal (`passed`/`failed`/`canceled`) runs beyond the limit are deleted, mirroring the existing webhook history retention; a `running`, `queued`, or manual-approval-pending run is never deleted. `KESTRIX_RUNNER_MAX_OUTPUT_BYTES` (default `10485760`, 10 MiB, also `runner.max_output_bytes`) bounds stored run output: output beyond the bound is dropped and the stored output ends with a marker line naming the bound, after secret redaction, without affecting the run's or any task's status. All three must be positive integers or startup fails naming the setting.
  - Upgrading an existing deployment applies retention starting from the first run to finish after the upgrade, which may prune a backlog of old runs down to the configured limit immediately; raise `KESTRIX_RUN_HISTORY_LIMIT` beforehand if that backlog should be kept longer.
- Webhook setup from the UI: the project create and edit dialogs now carry a **Webhook secret** field (masked, with a reveal toggle) and a **Pipeline file** field, and the project detail page gains a **Webhook setup** panel with the delivery URL (`<origin>/webhook`), a copy button, and the GitLab steps. The detail header shows whether a per-project secret is stored, derived from `has_webhook_secret`, and warns when none is - deliveries then depend on the global `KESTRIX_WEBHOOK_SECRET`. A stored secret is never returned by the API and is never rendered: the edit dialog starts empty and omits `webhook_secret` from the update unless a new value is typed, so saving any other field cannot clear it. The panel names both accepted header forms (`X-Gitlab-Token`, `X-Hub-Signature-256`) and states that the server's configured method decides which is verified. No backend change; registering a project's webhook no longer requires Swagger or `curl`.
- First-run administrator setup: a fresh instance with no accounts serves `GET /api/setup` (`{"required": true|false}`) and `POST /api/setup` (`{name, password}`) without authentication. Setup creates the first account with the `admin` role, succeeds exactly once - concurrent requests race safely, and every request after the first account exists answers `409` and changes nothing - and is throttled per client address with the same limits as login. The UI checks setup status before showing the login form and presents a "Create the first administrator" form in its place while a fresh instance has none, signing the new account in on success. `kestrix user create --role admin` remains an equivalent, scriptable alternative; whichever runs first closes the other.
- Browser sessions now use an `HttpOnly` cookie (`kestrix_session`) instead of a token held in page-readable storage: `POST /api/auth/login` sets it alongside the existing bearer response, `POST /api/auth/logout` clears it, and `GET /api/auth/me` returns the signed-in account's name, role, and expiry so the UI can restore a session it can no longer decode. A cookie-authenticated mutation must carry the `X-Kestrix-Request` header or is rejected with `403`; bearer clients (CLI, scripts, the Terraform provider) are unaffected and need no change. `KESTRIX_COOKIE_SECURE` (default `true`) controls the cookie's `Secure` mark for plain-HTTP development. Every open browser session is signed out once on upgrade and must log in again.
- Multi-source projects: every registered project now has a derived, read-only set of sources - its `repo_url` plus every `ci_repo` in its pipeline that declares a `url` - stored in the new `project_sources` table and exposed as `sources` on `GET /api/projects/{name}` and on the Projects page. `POST /webhook` resolves deliveries by matching the payload's repository URLs against those sources (transport-neutral, so HTTPS and SSH forms match), falling back to `gitlab_project_id` as before, and verifies the delivery against each matched project's own `webhook_secret` (or the global secret) before processing it. A push to a secondary repository loads the pipeline from the primary repository at its configured `repo_ref`, marks that `ci_repo` as changed, and passes `KESTRIX_SOURCE_NAME` / `KESTRIX_SOURCE_REVISION` to the dispatched job. One repository declared by several projects fans out to each of them; the response gains a `results` list with one entry per project (the single-match document keeps its previous top-level keys). Webhook history rows and `GET /api/logs` items carry `source_name`.
  - Startup creates the table, adds `webhook_events.source_name`, and backfills the primary source for existing projects; open each project once after upgrading so its remote `ci_repo` blocks are derived as sources.
  - A secondary repository only reaches Kestrix if a webhook is registered on it in the Git host, pointing at the same `/webhook` URL and presenting a secret one of the matched projects accepts.
- Run attribution: runs now record `started_by` and `canceled_by`, and a manual task's result entry records `approved_by`/`approved_at`, as the `user:<account name>` that acted. Kestrix logs one line per start, approval, and cancellation naming the actor, project, run id, and (for an approval) the task name. The two new `runs` columns are added automatically at startup by the existing idempotent schema statements - no manual migration step is needed. A run recorded before this change shows `unknown` in the UI.
- Session revocation: an account's global role, password, and token version are now resolved from the database on every request instead of trusted from the token, bounded by a short-lived in-process cache (`KESTRIX_IDENTITY_CACHE_TTL`, default `5s`, `0` disables it). Changing a role or password, or deleting an account, ends every session issued before the change - the account must log in again.
- Login throttling: `POST /api/auth/login` limits failed attempts per account name and per client address (`KESTRIX_LOGIN_MAX_ATTEMPTS`, default `10`; `KESTRIX_LOGIN_WINDOW`, default `1m`), returning `429` with `Retry-After` and skipping password verification once throttled. `KESTRIX_TRUST_PROXY_HEADER` (default `false`) opts into keying the client address from `X-Forwarded-For` behind a trusted reverse proxy.
- Security response headers on every route: `Content-Security-Policy` (overridable via `KESTRIX_CONTENT_SECURITY_POLICY`, `/docs/*` keeps its own), `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`, and `X-Frame-Options: DENY`.
- Authentication and authorization decisions (failed logins, throttled attempts, `403` denials) are now logged with the account, client address, route, and reason - never the token, password, or password hash.
- Local user accounts, JWT-based login, and role-based access control (`viewer`/`operator`/`admin`, plus per-project role grants). `POST /api/auth/login` and admin-only account endpoints (`/api/users*`) are new.
- `kestrix user create|list|passwd|delete` manages accounts directly against the database, so the first administrator can be created without a reachable API or an existing account. Passwords are always read from a terminal prompt or standard input, never a flag.
- The Settings page gains an Accounts section, visible only to an admin, that lists every account with its global role and project grants, and lets an admin create, promote, grant, and delete accounts without scripting the `/api/users*` endpoints directly. No backend change.
- `KESTRIX_JWT_SIGNING_KEY_PATH` configures the token signing key, provisioned and validated at startup the same way as `KESTRIX_MASTER_KEY_PATH`.
- The UI requires sign-in before showing any data, attaches the session token to every request, and hides actions the signed-in role cannot perform (server-enforced regardless of what the UI shows).
- Durable webhook history: every parsed webhook event is recorded in PostgreSQL and survives a server restart, including events that are ignored, skipped, or failed. Requests rejected before their payload is parsed are not recorded.
- `KESTRIX_WEBHOOK_HISTORY_LIMIT` (default `1000`, also `webhook.history_limit` in the config file) bounds retained webhook events; the oldest are discarded once the limit is exceeded.
- `GET /api/logs` accepts `project`, `status`, `since`, and `until` filters alongside `limit` and `offset`.
- The Webhook Logs page offers project, status, and date-range filters with pagination, and shows explicit empty and error states.
- HTTP listener timeouts (`KESTRIX_HTTP_READ_TIMEOUT`, `KESTRIX_HTTP_WRITE_TIMEOUT`, `KESTRIX_HTTP_IDLE_TIMEOUT`; defaults `30s`/`120s`/`120s`) and per-route request-body bounds (`KESTRIX_HTTP_MAX_BODY_BYTES` for `/api`, default `1048576`; `KESTRIX_WEBHOOK_MAX_BODY_BYTES` for `POST /webhook`, default `8388608`). A request over its bound answers `413` without running the route's business logic; each setting must be a positive value or startup fails with an error naming it.
- Each project's `webhook_secret` is now a real, verified control: `PUT /api/projects/{name}` can set a per-project secret checked against every delivery for that project, alongside the existing global `KESTRIX_WEBHOOK_SECRET`.
- `repo_url` scheme and host restrictions: only `https://`, `ssh://`, and scp-like `user@host:path` are accepted; a literal loopback, link-local, or unspecified host — including one written as a decimal, octal, hexadecimal, or short-form IPv4 literal (e.g. `2130706433` or `0x7f000001` for `127.0.0.1`) — is rejected, all with `400` before any network access.
- Run-time secrets: a new `secret` credential type holds one opaque value, created and managed through the same `/api/credentials` endpoints, `admin` role, master key, and Settings UI as Git credentials. A pipeline `variable` block can set `secret_ref` to reference one instead of a literal `value` or `default` - `secret_ref` cannot be combined with either, and a `secret_ref` variable is always masked regardless of the `masked` attribute. Every `secret_ref` is resolved once, when a run or an approved manual task starts; a missing, revoked, or non-`secret` reference fails the run before any task starts, naming only the variable, and records every task `skipped`. Resolved values of at least 8 bytes are redacted (`***`) from run and task output before it is persisted, flushed, or returned by any API; a `secret` credential is refused as a repository credential and vice versa, in both directions.

### Changed

- **BREAKING**: licensing is now consistent across the repository, and it is not MIT. `LICENSE` carries the full text of the [PolyForm Noncommercial License 1.0.0](LICENSE), which permits noncommercial use only - personal projects, evaluation, study, hobby work, academic research, and use by charitable, educational, public research, public safety, health, environmental, and government organizations. Commercial use now requires the separate commercial license described in [LICENSE-COMMERCIAL.md](LICENSE-COMMERCIAL.md), priced by total user accounts per [PRICING.md](PRICING.md). The previous files contradicted each other: `LICENSE` said "all rights reserved, evaluation only", `README.md` said "MIT", and `PRICING.md` pointed at a `LICENSE.md` that did not exist. Anyone who relied on the README's MIT statement should re-read `LICENSE`. No code enforces a plan, an account limit, or a license key.
- **BREAKING**: `docker/docker-compose.prod.yml` no longer ships a shared default database password: `POSTGRES_PASSWORD` is now required, and both the `postgres` container and the Kestrix `DATABASE_URL` use it. An existing deployment must add `POSTGRES_PASSWORD=kestrix` to `.env` before upgrading (the password already in its volume), then rotate it with `ALTER USER kestrix WITH PASSWORD '...'` if desired. PostgreSQL is also no longer published on the host by default - opt in with `--profile db-port` and `POSTGRES_PORT` (binds to `127.0.0.1` unless `POSTGRES_BIND_HOST` overrides it) - and the `business` marketing-site container now requires `--profile business`; a plain `up -d` starts only `kestrix` and `postgres`. A new `proxy` service (Caddy, `--profile tls`, requires `KESTRIX_DOMAIN`) terminates HTTPS with an automatic certificate and forwards to Kestrix; set `KESTRIX_TRUST_PROXY_HEADER=true` alongside it (never automatic, since `kestrix` always starts regardless of profile). See [docs/deployment.md](docs/deployment.md) for the full install, upgrade, backup, and TLS walkthrough.
- **BREAKING**: a burst of triggers (a webhook fanning out to several projects, several pushes in quick succession) no longer starts every run in parallel: at most `KESTRIX_RUNNER_MAX_CONCURRENT_RUNS` (default `2`) execute at once, and the rest are queued. A deployment that relied on unbounded parallelism should raise this setting before upgrading.
- On startup, before the HTTP listener opens, Kestrix now fails every run left `running` or `queued` by a previous instance (crash, redeploy, `docker compose up -d`): the run is marked `failed` with error `interrupted by server restart`, its non-terminal task results are marked `failed` (was `running`) or `skipped` (was `pending`) with the same error, and the run's output gains a trailing line naming the interruption. A run only waiting on manual approval is left alone and remains approvable. Previously such runs stayed `running` forever, showing as ghosts in run lists, dashboard counters, and `GET /api/runs?status=running`. Kestrix supports exactly one `serve` process per database; see `docs/architecture.md`.
- **BREAKING**: configuration precedence is now one rule for every setting: explicit CLI flag over config-file value over `KESTRIX_*` environment over default. Four settings flip from env-wins to file-wins: `webhook.secret`, `webhook.history_limit`, `dispatch.project_id`, and `dispatch.gitlab_token`. An operator who committed a placeholder to `config.yaml` and relied on the environment to override it must delete the key from the file; deployments without a `config.yaml` (Compose) are unaffected. Three previously inert forms now take effect when the file omits the matching key: `KESTRIX_ADDR`, `KESTRIX_DIR`, and `KESTRIX_GITLAB_URL`. The removed `docker:` config block, `-docker-registry`, `-docker-image`, `-docker-username`, `-docker-password` flags, and `runner.executor` key fail startup as unknown keys: an unknown key in `config.yaml` now exits non-zero naming the key and file path, never the value. `DOCKER_*` remain only as host variables forwarded to tasks through `KESTRIX_RUNNER_ENV_PASSTHROUGH`.
- **BREAKING**: Every token carries a per-account version now; a token issued before this upgrade carries none and is rejected with `401`, so every signed-in session must log in again once. The `users` table gains a `token_version` column, added automatically on startup - no manual migration step is required.
- A grant-store or user-store failure during authorization now responds `503`, never a silently reduced role or a `403` that blames the caller for an outage; and a caller-supplied pipeline directory (`dir` on `/api/pipeline`, `/api/pipeline/raw`, `/api/resolve`, `/api/generate`, `/api/validate`) is now confined to the configured pipeline root, answering `403` for a path outside it (including one that doesn't exist, so the check cannot be used to probe the filesystem).
- **BREAKING**: Every `/api` route except `GET /api/health` and `POST /api/auth/login` now requires a valid bearer token; an existing deployment must set `KESTRIX_JWT_SIGNING_KEY_PATH` and run `kestrix user create --role admin <name>` before upgrading, or the server starts but the UI and API are unusable. `POST /webhook` is unaffected: it keeps its own shared-secret verification.
- **BREAKING**: `POST /webhook` verification now fails closed. A delivery is accepted only if it verifies against the matched project's own `webhook_secret` or the global `KESTRIX_WEBHOOK_SECRET`; a delivery that verifies against neither - including when neither is configured at all - is rejected with `401` and is never recorded in webhook history. The Compose files' `KESTRIX_WEBHOOK_SECRET:-dev-secret` default is removed: an existing deployment with no secret set stops accepting deliveries until `KESTRIX_WEBHOOK_SECRET` or a per-project secret is configured. Secret comparison is constant time; the previous `!=` comparison and the `KESTRIX_WEBHOOK_METHOD=hmac` setting (previously accepted by config but never honored) are fixed.
- **BREAKING**: `webhook_secret` is now write-only on the project API: `GET /api/projects`, `GET /api/projects/{name}`, `POST /api/projects`, and `PUT /api/projects/{name}` no longer return it in any form, and each response instead carries `has_webhook_secret`. An update that omits `webhook_secret` (or sends it empty) now keeps the stored secret unchanged, instead of silently clearing it - the previous behavior meant every UI save wiped a secret set via the API, since the UI never sent the field.
- **BREAKING**: `GET /api/logs` returns the paginated `{items, pagination}` envelope already used by `/api/runs` and `/api/projects`, instead of a bare JSON array.
- `GET /api/health` reports the stored webhook count and the registered project count as separate values; both fields previously echoed the same in-memory counter.
- `GET /api/health` responds `503 Service Unavailable` with `"status": "degraded"` and omits a counter whose store query failed, instead of reporting a healthy zero behind a 200. The Compose healthchecks and `scripts/deploy.sh` read the HTTP status only, so a degraded runtime now actually fails them.
- A webhook whose GitLab pipeline dispatch fails is recorded with status `error` rather than `triggered`, so `GET /api/logs?status=error` finds it.
- **BREAKING**: task processes in every runner mode (`local`, `docker`, `gitlab-runner`) now receive an explicit environment allowlist instead of the full Kestrix process environment: a fixed base set (`PATH`, `HOME`, `LANG`, `LC_ALL`, `TMPDIR`, `TERM`, `USER`), the `CI_*` variables Kestrix sets, the pipeline's own resolved variables, and only host variables named in the new `KESTRIX_RUNNER_ENV_PASSTHROUGH`. `KESTRIX_MASTER_KEY_PATH`, `KESTRIX_JWT_SIGNING_KEY_PATH`, `DATABASE_URL`, `KESTRIX_GITLAB_TOKEN`, and `KESTRIX_WEBHOOK_SECRET` can never be passed through - listing one refuses to start. A pipeline that relied on an inherited host variable must list it; this repository's own dogfood deployment sets `KESTRIX_RUNNER_ENV_PASSTHROUGH=DOCKER_REGISTRY,DOCKER_IMAGE,DOCKER_USERNAME,DOCKER_PASSWORD,DEPLOY_HOST,KESTRIX_TEST_DATABASE_URL`.
- `docker` runner mode now runs every task container with `--cap-drop ALL`, `--security-opt no-new-privileges`, a PID limit (`KESTRIX_RUNNER_DOCKER_PIDS`, default `256`), a memory limit (`KESTRIX_RUNNER_DOCKER_MEMORY`, default `2g`), and a CPU limit (`KESTRIX_RUNNER_DOCKER_CPUS`, default `2`); network is configurable via `KESTRIX_RUNNER_DOCKER_NETWORK` (default `bridge`, `none` disables egress) and an optional non-root user via `KESTRIX_RUNNER_DOCKER_USER`. The Docker socket is never mounted and `--privileged` is never passed.
- Cancelling a run now terminates its executing task before the run is recorded as `canceled`: `local` and `gitlab-runner` mode send the task's process group SIGTERM then SIGKILL, and `docker` mode stops the container, after `KESTRIX_RUNNER_CANCEL_GRACE` (default `10s`). A run whose task cannot be confirmed terminated within grace plus 5s stays `running` and the cancel request fails with `504`, instead of falsely reporting `canceled`.
- The `runner:` config-file block now takes effect: `runner.docker_pids`, `runner.docker_memory`, `runner.docker_cpus`, `runner.docker_user`, `runner.docker_network`, and `runner.cancel_grace` previously had no effect and only the matching `KESTRIX_RUNNER_*` environment variables worked. Where both the config file and the environment variable are set to different values, the config file now wins, per `runtime-configuration` precedence.

### Removed

- The `redis` Compose service and `redis_data` volume, from both the development and production profiles: no Go code ever connected to it. `REDIS_PORT` is removed from `.env.template` and `scripts/docker-deployment-e2e.sh`. An existing deployment keeps its orphaned `redis_data` volume until an operator runs `docker volume rm`; `docker compose up -d --remove-orphans` stops and removes the running container. The Terraform provider's resource schema and examples move to their own repository; `docs/terraform-provider.md` is now a pointer to it.

### Fixed

- Cancelling a single-task re-run or an approved manual task now terminates the task's process group (SIGTERM, then SIGKILL after `KESTRIX_RUNNER_CANCEL_GRACE`) and records the run as `canceled`: previously only the stored status was rewritten while the process kept running, and a late local verdict could overwrite the cancellation. A run already `canceled` also keeps that status against late writes.
- The Webhook Logs page no longer falls back to fabricated sample events, and no longer calls a hard-coded `http://localhost:8080`, which broke the Docker deployment profile on port `18080`.
- An approved manual task in a project configured for `docker` mode now runs in the same hardened container as a DAG task (dropped capabilities, PID/memory/CPU limits, configured network and user); previously manual approval always ran the task with a bare `bash -c` on the host regardless of the configured runner mode, bypassing that hardening entirely.
- A `secret`-typed `credential_ref` on a secondary `ci_repo` is now rejected with `400` at project create/update time, the same rule already applied to the primary `repo_credential_ref`. Previously it was accepted at create/update and only failed later, at source-acquisition time, with a less direct error.

## [v0.2.0] - 2026-07-31

### Added

- PostgreSQL-backed runtime with separate local-development and deployment databases.
- Docker-based local development and production deployment profiles.
- Dedicated Docker Compose naming and port separation for development and deployment environments.
- Docker pipeline execution support, including image build and deployment health checks.
- Business website deployment through a dedicated Nginx container.
- Manual pipeline task approval and run-status handling in the UI.
- Additional unit, integration, and regression coverage for runtime, web, runner, and deployment behavior.

### Changed

- Kestrix is now the canonical project and binary identity throughout the runtime and documentation.
- `make docker-up` starts development dependencies only; `make docker-up-all` also starts the Kestrix development container.
- Local development uses PostgreSQL on port `5433` and Redis on port `6380`.
- Docker deployment uses PostgreSQL on port `5432`, Redis on port `6379`, and Kestrix on port `18080`.
- Frontend lint/build checks are more reliable and include a `make format` convenience target.
- Project registration and pipeline configuration no longer depend on the legacy `demo-mono` startup fixture.

### Fixed

- Deployment no longer stops the local development backend, preventing browser `NetworkError` failures during manual deployment.
- Docker Compose container-name and project collisions between local and deployed environments.
- Runtime startup and test configuration now consistently require PostgreSQL instead of the removed file store.
- Frontend lint warnings and build failures caused by stale output permissions and unused code.

### Release notes

- The previous release tag was `0.1.1`.
- Release tags use the `v` prefix from this release onward: `v0.2.0`.
