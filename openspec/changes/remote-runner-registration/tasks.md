- [ ] 1.2 Add `RemoteJobStore` (or extend `RunStore`) port in `internal/domain/ports.go`: `ClaimNextJob(runnerID string) (*RemoteJob, error)` via `SELECT ... FOR UPDATE SKIP LOCKED` (returns a nil `*RemoteJob` when nothing is pending, incrementing `claim_epoch` on a successful claim), `AppendJobTrace(jobID int, epoch int, chunk string) (ok bool, err error)` (`ok` false when `epoch` no longer matches the job's current `claim_epoch` — see design.md D1; stores via a database-side append, `UPDATE runs SET output = output || $1`, never `FlushRunOutput`'s whole-column overwrite — design.md D9; the append itself enforces `max_output_bytes`, cutting the crossing chunk at the bound, appending the truncation marker once and discarding later chunks, since no in-process `boundedWriter` sits on this path), `CompleteJob(jobID int, epoch int, status, output string) (ok bool, err error)` (same epoch-fencing shape, and in the *same* transaction as the epoch check it re-reads the parent run's status under lock and returns `ok` false when that run is already terminal — the two checks must not be layered in the handler, or a run that goes terminal in between is still resumed); verify with unit tests covering the claim race (two concurrent claims, one job) and epoch rejection (append/complete with a stale epoch is a no-op)
- [ ] 1.3 Add `RunnerStore` port: `CreateRunner(name string) (id int, token string, err error)` (token generated, hashed before storage), `AuthenticateRunner(token string) (runnerID int, ok bool, err error)` (constant-time), `RevokeRunner(id int) error`; verify with unit tests including revoked-token rejection

## 2. Mode: remote

- [ ] 2.1 Add a `Mode` field to `domain.ProjectConfig` accepting `local`/`docker`/`gitlab-runner`/`remote`, with a migration defaulting existing rows to the current instance-wide `config.RunnerConfig.Mode`; replace the single shared `runner.PipelineExecutor{Mode: cfg.Runner.Mode}` construction in `internal/web/server.go` with per-project executor selection at dispatch time, keyed on the project's own `Mode`; verify with unit tests covering the migration default, an unrecognized value being rejected, and two projects on the same instance dispatching under different modes concurrently
- [ ] 2.2 On run start for a `remote`-mode project, dispatch each task as a `remote_jobs` row instead of calling `Executor.RunTask` in-process, with the job payload containing only the task's resolved pipeline variables (no control-plane variable, per the `task-execution-isolation` delta) and a source archive built from the checkout Kestrix already acquires server-side (design.md D6) — no repository credential in the payload; verify with unit tests asserting the payload excludes `DATABASE_URL`/every `KESTRIX_*` variable even when `KESTRIX_RUNNER_ENV_PASSTHROUGH` names one, excludes any repository credential value, and asserting a `remote_jobs` row is created per task with no in-process `Executor.RunTask` call — and covering the archive-building step against an empty-repo checkout and an oversized-repo checkout (design.md Risks: per-task archive multiplication); also verify the constructed payload contains no field naming a container engine or image (design.md D3, Requirement: Runner selects its own execution engine)
- [ ] 2.3 Assert a `remote`-mode run's tasks do not occupy an in-process concurrency slot; verify with a unit test starting a remote-mode run while `max_concurrent_runs` slots are all busy and asserting immediate dispatch
- [ ] 2.4 Gate every entry point that executes a task on the project's `Mode`, not just `Start` (design.md D10): `RunTask` (single-task re-run) and `ApproveManualTask` (manual gate) both reach `runTaskInternal` → `taskRunner.RunTask` with no mode check today and would run a remote-mode task in-process; for a `remote`-mode project each dispatches a single job instead, and the completion path records output by appending (D9), never by `ApplyTaskResult`'s read-modify-write of the `output` column. The gate does not stop at `RunService`: `internal/web/handler_run.go`'s `handleRunTask` treats `RunTask`'s return value as a terminal result and calls `FinishRun` on it, which for a dispatched-not-executed task would finalize the run as `passed` with empty output before any runner polls — and the runner's real completion would then hit the terminal-run guard and record nothing. `RunTask`'s own return contract changes to make this representable: it returns a `Dispatched bool` alongside its existing `(domain.TaskResult, error)` (or an equivalent sentinel), true when the task was handed to a runner rather than executed. `handleRunTask` branches on that value alone — never on `proj.Mode` itself, which stays owned by `RunService`, the same layering D10 already chose for `Cancel` — and when `Dispatched` is true it responds with the queued, non-terminal run and calls no finalizing method; the same applies to any other caller that finalizes from a task-execution return value. In `RunService.Start`, skip the in-process half for a `remote`-mode project — no goroutine, no `active`/`done` entry, no slot — so `Cancel`'s existing no-active-entry branch provides the carve-out's semantics with no mode-conditional added to `Cancel` (design.md D10); extend `ActiveRunIDsForProject` with a store-backed check for runs holding outstanding (`pending`/`claimed`/`running`) remote jobs, unioned with the in-memory set, returning an error the delete handler treats as fail-closed (refuse the deletion) rather than fail-open — the invariant the archived `project-delete-run-guard` D1 protected; verify with unit tests that a remote-mode run registers no active entry, that a single-task re-run and an approved manual task on a remote-mode project each create a job and invoke no in-process executor, that `RunTask` returns `Dispatched: true` for one, that `handleRunTask` — driven only by that return value, not by re-checking `proj.Mode` — responds with the queued run and calls no finalizing method so the runner's later completion is the one that records the result, and — the negative case, since `Dispatched` is a new field on `RunTask`'s shared return and a flipped condition or a bool defaulting to `true` would pass every test above while breaking every non-remote project — that a `local`/`docker` single-task re-run and an approved manual task still return `Dispatched: false` and that `handleRunTask` still finalizes through `FinishRun` exactly as it does today, that `Cancel` on it succeeds without entering the termination-and-wait path, that deleting a project with an outstanding remote job is still refused, and that a store error on that check refuses the deletion rather than allowing it

## 3. Runner-job endpoints

- [ ] 3.1 Add the runner-job route group outside `/api` in `buildRouter`, with its own bearer-token middleware (constant-time, rejects a user session or an `/api` token) and its own `maxBody` bound (a new `RunnerJobMaxBodyBytes` config setting, same pattern as `WebhookMaxBodyBytes`) plus a per-token cap on concurrent open long-polls against `next`; verify with unit tests for each rejection case, an oversized-body rejection paired with an at-the-limit body that is accepted (the bound rejects only what *exceeds* it), a rejection once a token's concurrent-poll cap is reached paired with a poll at exactly the cap that is accepted, and — the reverse direction — that a runner token presented to any `/api` route is rejected `401` and never resolves to an account or role (access-control spec's "Runner token does not authenticate `/api`")
- [ ] 3.2 Implement `GET /api/runner-jobs/next` as a bounded long-poll calling `ClaimNextJob`, returning `204` on no work or `200` with the payload; verify with unit tests asserting the exactly-once claim under two concurrent pollers, and that a poll with no pending job blocks for the bounded interval then returns `204` (not an error)
- [ ] 3.3 Implement `PATCH /api/runner-jobs/{id}/trace` (offset-based), rejecting the append as a no-op when the request's claim epoch no longer matches `AppendJobTrace`'s `ok` result, and otherwise routing appended content through the existing `redactingWriter` before the appending store write (D9); verify with unit tests that a known secret value in the chunk is redacted before storage, that two concurrent appends for two different jobs of the same run both survive (neither overwrites the other), that appends past `max_output_bytes` are dropped leaving the stored output at the bound plus a single truncation marker while the job still completes normally, that a stale-epoch append is rejected and not stored, that a malformed chunk (missing/non-numeric offset) is rejected with an error rather than stored, and offset correctness — a duplicate offset is a no-op, an out-of-order or gapped offset is rejected rather than silently misplacing content (oversized-chunk rejection is covered by 3.1's body-size bound)
- [ ] 3.4 Implement `PUT /api/runner-jobs/{id}/complete` as a thin adapter into a new `RunService` method — not because `internal/web` never calls a `RunStore` completion port directly today (it does: `handleRunTask` and `handleResolve`'s secret-error path both call `s.runStore.FinishRun` directly, and `FinishRun` sits on the same `domain.RunStore` interface as `AppendTaskResult`), but because the epoch check, the terminal-run guard and the resumption step (3.6) are new business logic this endpoint needs, and `RunService` is where run-lifecycle logic already lives for every other write path — which rejects the report as a no-op when `CompleteJob`'s `ok` result is false (stale or already-completed epoch), and otherwise records the task result and invokes task 3.6's resumption step for dependents — the endpoint itself owns none of that logic; verify with unit tests asserting a dependent task becomes eligible after its only dependency completes via this endpoint, that a duplicate completion for the same epoch does not re-record the result or re-resume the run's dependency graph, that completion under an epoch superseded by reclaim (4.2) is rejected, that a completion arriving for a run already `passed` (its last job completed first) records nothing and leaves the run `passed`, that a completion whose run turns terminal between the epoch check and the result write is rejected (interleaving test, e.g. a sibling job failing the run in that window), and that a completion arriving for a run already in a terminal status stores output only — asserted against a run failed by `FailInterruptedRuns` (which knows nothing about `remote_jobs`, so the runner's epoch is still current), not only against a canceled one, since `ApplyTaskResult` otherwise recomputes the run's status from scratch and would revive it
- [ ] 3.5 Implement `POST /api/runners` (admin-only, `RequireRole(domain.RoleAdmin)`) returning the token once, and `DELETE /api/runners/{id}` (also admin-only) for revocation; verify with unit tests for the success path of each, plus a separate non-admin `403` test per endpoint — one for `POST /api/runners`, one for `DELETE /api/runners/{id}` (access-control spec's "Runner management requires admin role" has a scenario for each)
- [ ] 3.6 Add a dependency-graph resumption step on `RunService` (the same method 3.4 calls, not a free function `internal/web` reaches into directly): given a run's persisted `task_results` and its pipeline snapshot, compute which not-yet-dispatched tasks have become eligible, applying `taskLoop`'s existing blocked/manual/ordering rules (a failed dependency blocks, a manual task waits for approval, declared order is respected) without `taskLoop`'s in-memory state; dispatch a job for each newly eligible task. This is new machinery, not reuse — design.md Goals; verify with unit tests over stored results for a diamond graph (both branches must finish before the join dispatches), a failed dependency (dependents stay undispatched), and a manual task (not dispatched until approved)

## 4. Silent-runner recovery

- [ ] 4.1 Add `KESTRIX_RUNNER_JOB_TIMEOUT` (default, e.g. `120s`) and a max-reclaim-count setting, following the established config precedence; verify with unit tests covering file/env/default resolution and invalid-value startup failure
- [ ] 4.2 Add a background check (alongside the existing run-scheduling loop) that returns a stale `claimed`/`running` job to `pending` and increments its `claim_epoch` (design.md D1/D5), or fails it after the configured max reclaims, naming the reason — skipping any job whose run is already in a terminal status, which is finalized in place instead (spec.md "Silent runner recovery"); verify with unit tests for both the reclaim (including that a subsequent `trace`/`complete` call under the old epoch is now rejected) and the final-failure path, plus tests that the terminal-run exclusion holds for every terminal status, not just `canceled`: a stale job of a `canceled` run is never returned to `pending`, and a still-`pending` job whose run already reached `failed` (a sibling branch's job exhausted max reclaims and failed the run) is never handed to a poller
- [ ] 4.3 On canceling a remote-mode run, mark its remaining `pending` jobs unclaimable and the run `canceled` without waiting for `claimed`/`running` jobs (no stop signal is sent — spec.md "Cancelling a remote-mode run"); make `ClaimNextJob` skip any job whose run is in a terminal status, so cancellation cannot be undone by the reclaim path (4.2); verify with unit tests that `RunService.Cancel` on a remote-mode run returns success promptly — no `CancelGrace + 5s` wait, no `ErrRunCancelTimedOut` — even while one of its jobs is still executing on a runner (the counterpart of the local/docker "Termination fails" coverage; 2.4 sets up the no-active-entry path this relies on), that a pending job is never claimed after its run is canceled, that a job left `claimed` when its run was canceled is neither reclaimed nor re-offered once it goes silent, and that a completion report arriving after cancellation stores its output but neither resumes the run's dependency graph, changes the run's terminal status, nor appends a task result that would supersede the `canceled` one `CancelRun` already wrote (`dedupLatestTaskResults` treats the newest row per task as authoritative)

- [ ] 5.3 Update `docs/ci-tools.md`'s Runner section: add `remote` to the mode table, and add a row to the Cancellation subsection stating that canceling a `remote`-mode run does not stop the runner's in-flight process, and that output from that process keeps arriving in the run's trace afterwards without reopening the run or changing its `canceled` task result — an operator watching a canceled run would otherwise read the late output as a bug; cite both specs that define this (`remote-runner-execution`'s "Cancelling a remote-mode run" and the `task-execution-isolation` MODIFIED delta carrying the grace-period mechanism and the `remote` carve-out), plus proposal.md Non-goals; also document that on a `remote`-mode project a single-task re-run and an approved manual gate dispatch a job to a runner rather than executing on the Kestrix host — asynchronous, no local process, output arriving over the runner-job protocol, so an approval does not mean the task has started until a runner claims it; and that a `remote`-mode run's trace may interleave two tasks' lines unpredictably — unlike every other mode, where one sequential writer owns the run's output, two jobs of one run can stream from two runners at once and only non-loss, not ordering, is guaranteed (design.md D9); verify by reading the updated doc against the shipped behavior
- [ ] 5.4 Add a `CHANGELOG.md` entry under Unreleased for the new `remote` project mode, `/api/runners`, and `/api/runner-jobs/*` — same class of entry as `archive/2026-09-10-runner-execution-isolation` and `archive/2026-09-15-orphan-run-recovery`; verify the entry is present
