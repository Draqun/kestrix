# CI Generator

The CI generator converts a resolved Kestrix pipeline into a standard `.gitlab-ci.yml` file. It maps task dependencies to GitLab's `needs` keyword, sets per-job container images, handles manual approval gates, and derives pipeline stages from the dependency graph.

## Overview

When a pipeline run starts, the DAG engine resolves which tasks are triggered and in what order. The CI generator takes that resolved list of DAG nodes and produces a GitLab CI YAML that can be:

- Written to disk and executed via `kestrix run` (local/Docker/GitLab-runner modes).
- Dispatched to a GitLab project via the dispatch client.
- Previewed via `POST /api/generate`.

## Stage Derivation

Stages are derived automatically from the dependency graph:

| Task Type | Stage Assigned |
|-----------|---------------|
| No dependencies, not manual | `build` |
| Has dependencies | `test` |
| Manual task | `deploy` |
| Dependencies mention "test" in name | `deploy` |

A pipeline only declares stages that are actually needed. For example, a pipeline with only build tasks generates a single `build` stage.

## Job Structure

Each triggered task becomes a GitLab CI job with:

- **Header**: Auto-generated comment with project name.
- **Stage**: Derived from dependencies (see above).
- **Image**: Per-task override or project-level default.
- **Needs**: Task dependencies mapped to GitLab's `needs` keyword.
- **When**: `manual` for tasks with `manual = true`.
- **Script**: Logs the task name and repo context, then runs the task's script command.

### Example Output

Given a pipeline with two tasks (`build` → `test`):

```yaml
# Auto-generated by Kestrix — do not edit manually
# Project: my-project

stages:
  - build
  - test

default:
  image: golang:1.22

build:
  stage: build
  script:
    - echo "Running build in repo my-repo"
    - ./build.sh

test:
  stage: test
  needs:
    - build
  script:
    - echo "Running test in repo my-repo"
    - ./test.sh
```

## Manual Tasks

Tasks with `manual = true` are assigned to the `deploy` stage and include `when: manual`:

```yaml
deploy:
  stage: deploy
  when: manual
  script:
    - echo "Running deploy in repo my-repo"
    - ./deploy.sh
```

## Per-Job Container Images

If a task specifies an `image` in its `execute` block, that image is used instead of the project default:

```yaml
test_integration:
  stage: test
  image: rust:1.75
  needs:
    - build
  script:
    - echo "Running test_integration in repo my-repo"
    - cargo test
```

## Usage

### CLI

```bash
# Preview the generated YAML for a pipeline
kestrix generate path/to/pipeline.tf
```

### API

```bash
curl -X POST /api/generate \
  -H "Content-Type: application/json" \
  -d '{"dir": "path/to/pipeline.tf", "changed": ["repo-a"]}'
```

Returns:

```json
{
  "yaml": "# Auto-generated by Kestrix...",
  "task_count": 3
}
```

### Runner Integration

When using `kestrix run` (local mode), the generator is called internally. The generated YAML is written to a temporary directory and executed against the selected runner.
